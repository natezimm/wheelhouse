# AGENTS.md

Guidance for coding agents working in this repository. The README covers what Wheelhouse is and how to run it; this file covers what you need to change it safely.

## Commands

Run these from the repository root unless a line says otherwise.

| Task | Command |
| --- | --- |
| Build the API and tests | `dotnet build` |
| API tests (Docker must be running) | `dotnet test` |
| One API test class | `dotnet test --filter "FullyQualifiedName~FamilyTests"` |
| One API test | `dotnet test --filter "DisplayName~A_family_sees_only_its_own_rows"` |
| Web tests, in `web/` | `npm test -- --watch=false` |
| One web spec file, in `web/` | `npm test -- --watch=false --include src/app/core/family.spec.ts` |
| Web tests by name, in `web/` | `npm test -- --watch=false --filter "is private"` |
| Web production build, in `web/` | `npm run build` |
| Wall/phone browser checks, in `web/` (build first) | `npm run test:e2e` |
| Whole app at http://localhost:8080 | `docker compose up --build -d` |
| Database only, for running from source | `docker compose up db -d` |
| API from source, port 5080 | `dotnet run --project src/Wheelhouse.Api` |
| Web dev server, port 4200, in `web/` | `npm start` |
| New migration | `dotnet tool restore`, then `dotnet ef migrations add <Name> --project src/Wheelhouse.Api --output-dir Data/Migrations` |

The Playwright browser checks use stubbed API responses to hold and reject writes at wall and phone sizes; they verify immediate rendering, draft preservation and uncertain-response reconciliation. CI installs Chromium and retains screenshots/traces in `calendar-browser-checks`. Install the browser locally with `npx playwright install chromium` before running these checks.

There is no linter. Prettier settings live in `web/.prettierrc` but are not enforced, and some files do not match them, so do not reformat files you are not otherwise changing.

The API tests start their own PostgreSQL with Testcontainers. They never use the Compose database.

## Architecture

**One web app, two layouts.** `web/` is a single Angular app. `/wall` is the wall display (a 1920 × 1080 touch screen in kiosk mode) and `/` is the phone layout. Both talk only to the API. Settings live only on the phone, under `/settings`; the wall has none. State lives in root-provided stores under `web/src/app/core/` that expose read-only signals; components are standalone, the app is zoneless, and small components keep their template and styles inline.

**API by feature.** `src/Wheelhouse.Api/` is ASP.NET Core minimal APIs in feature folders (`Families`, `Demo`, `Auth`, `Devices`, `Calendar`, `Weather`, `Sessions`, `Health`). Each feature exposes a `MapX()` extension that `Program.cs` calls.

**Instance mode.** The same image runs as two kinds of instance, chosen by `Wheelhouse:Mode` (`WHEELHOUSE_MODE` in a deployed instance's `.env`):

- `Family` is a real family's private instance. Nothing is readable without signing in. It is the default when the setting is missing, and it must stay the default.
- `Demo` is the public demo. Each visitor gets a private copy of a fictional family (`Demo/DemoCopies`) and is signed in to it as a parent. A copy is a family row with `ExpiresAt` set, deleted an hour or less after it expires. A real family has no `ExpiresAt`, so cleanup can never delete one.

Local development and `docker compose up` run as `Demo`.

**Family scoping.** Every table that holds a family's data implements `IFamilyOwned`. `WheelhouseDbContext` gives each of those a query filter on `CurrentFamilyId`, which comes from the signed-in principal's `wheelhouse:family` claim through `ICurrentFamily`. Outside a request there is no current family and filtered queries return nothing. Code that runs without a request, such as the demo seeder, must opt out with `IgnoreQueryFilters()` on purpose.

**Authorization.** Everyone is authenticated by one encrypted cookie that carries their family's id. On a demo instance `POST /api/demo/visit` issues it; that endpoint is the only sign-in without an account and answers 404 on a family instance. The web app calls it in an app initializer, so the cookie exists before any screen loads data. On a family instance a parent signs in with Google: `GET /api/auth/google` sends the browser to Google, which returns it to `/api/auth/google/callback`, where `ParentSignIn` admits only verified addresses listed in `Wheelhouse:ParentEmails` and links each Google account (`UserAccount`, by Google's subject id) to a parent member. The first parent to sign in creates the family. A parent's cookie also carries their account id and is re-checked on every request, so removing them from the family or from the list signs them out. Google is used for identity only here; Calendar access is a separate connection (see Calendar). A wall display signs in by pairing (`Devices/Pairing`): it asks `POST /api/pairing` for a 6-digit code, a parent enters the code on their phone (`POST /api/devices`), and the display's next `POST /api/pairing/{id}/finish` gives it the same cookie, carrying its device id instead of an account. The cookie lasts a year and slides; each request re-checks the device row and updates its `LastSeenAt`, so a parent removing the display from Settings signs it out at once. A display reads the family but is not a parent. On the demo, a wall starts with its own copy and its "Pair with a phone" button joins the phone's copy. The demo never calls Google. Endpoints require the `Family` policy (anyone signed in to a family) or the `Parent` policy. `Family` is also the fallback, so an endpoint that names no policy still needs a sign-in; anything only a parent may do needs `RequireAuthorization(Policies.Parent)`. Only `/health`, `/api/session`, `/api/demo/visit`, `/api/auth/google` and the display's two pairing endpoints are open, through `AllowAnonymous()`, and `AccessTests` fails if that list changes.

**Calendar.** Google Calendar is the source of truth for events; the API keeps a cache of it. `CalendarSource` is one Google calendar the family shows, owned by a member or, with no member, by the whole family, and `EventInstance` is one occurrence of an event, as Google expands recurring ones. A timed event is stored as UTC instants, an all-day one as dates with an exclusive end, as Google does. `GET /api/calendar?from=&to=` takes the family's own days, in its time zone, and the web app turns instants into days with `core/days.ts` rather than the browser's zone. The demo seeds a copy's calendars in `Demo/DemoCalendar`, relative to the day the copy is made, and never calls Google. Anyone signed in to the family, a paired wall included, adds, changes and deletes events through `/api/calendar/events` (`EventEndpoints`): each change goes to Google first with the cached occurrence's etag in `If-Match`, then the cache takes what Google stored. Google's 412 answers 409 with Google's current version, which the screens show instead; a change to one occurrence of a repeating event changes only that occurrence. A new event can repeat daily, weekly or monthly (`EventRepeat`, sent to Google as an RRULE), and `?series=true` on a change or delete applies to the whole series (`EventSeries`): Google's series is patched through its first event, every occurrence keeps its own day, and the calendar is read again at once because Google gives the occurrences new versions and often new ids. On the demo the change goes straight to the copy's cache, which expands a new series itself. A calendar the shared account cannot write to (`CanWrite`) is shown but takes no changes.

**Google connection.** A family's calendars come from one shared Google account, not from the parents' own. A parent connects it from Settings: `GET /api/calendar/google/connect` sends the browser to Google's consent screen for Calendar with offline access, and `/api/calendar/google/callback` stores the refresh token in `GoogleConnection`, encrypted with Data Protection (`GoogleTokens`), whose keys live on their own volume. The consent's `state` is signed and names the family, so a code cannot be attached to another family. `GET`/`PUT /api/calendar/sources` list the account's calendars and choose which show and whose each is; without a connection (the demo) they list the calendars the family already has. Google's `invalid_grant` marks the connection `NeedsReauth`; Settings asks a parent to connect again, and `GET /api/calendar` says `needsReconnect` so the wall shows a notice. On a family instance `CalendarSyncService` syncs every connected family every two minutes (`CalendarSync:Interval`), and at once after a parent connects or chooses calendars (`CalendarSyncTrigger`). `CalendarSync` asks each calendar what changed since its sync token and only then, or once a day as the window moves, reads its events from 30 days back to 180 ahead and replaces the cache; Google's 410 for an old token means a full read. The `calendar` health check turns `Degraded` when a pass fails or a connection needs reconnecting. Wall and phone subscribe to committed calendar changes through SignalR and fetch their visible days when notified. A shared 30-second recovery check catches missed notifications; Google’s two-minute worker still discovers upstream edits. The tests turn the worker off and run `CalendarSync` themselves. All Google calls go through `IGoogleCalendar`; `GoogleCalendarApi` is plain HTTP to Google's REST endpoints, and the tests replace it with a fake. `/privacy` is the page Google asks for before the OAuth app can be published.

**Weather.** `GET /api/weather` is today's weather where the family lives, from Open-Meteo (no key), cached for 30 minutes per place, so demo visitors share one forecast. A parent sets the place from their phone in Settings (`PUT /api/family/location`), kept to two decimal places. With no place it answers 204, and 503 when Open-Meteo cannot be reached; the screens then leave the weather out. Tests replace Open-Meteo's handler and never call it.

**Startup.** `PrepareDatabaseAsync` applies migrations before the API takes requests. If the database cannot be reached the process exits and the container's restart policy retries.

**Configuration is read late.** Read settings inside a DI factory or through `IOptions`, not from `builder.Configuration` while registering services. The integration tests add their overrides in a way that only takes effect once the host is built, so an early read sees the wrong database or mode.

**Deploy.** Pushing a `v*` tag runs `release.yml`: tests, images to GitHub Container Registry, then `deploy/deploy.sh` on the server, which moves every instance under `~/wheelhouse/*/` to that version. Each instance is its own Compose project from `deploy/compose.yaml` with its own database, network and secrets. `deploy/new-instance.sh` creates an instance's folder, `.env` and nginx site on the server; `deploy.sh` warns about a family instance whose Google sign-in is not filled in. The server's nginx terminates HTTPS and forwards to the instance's web container on a loopback port; that container serves the Angular build and forwards `/api`, `/hubs` and `/health` to the API. The API reads `X-Forwarded-Proto` and `X-Forwarded-For` from the server's nginx, so it knows a visitor came over HTTPS and marks the sign-in cookie `Secure`.

**Look and feel.** Colors and fonts are design tokens in `web/src/styles.css`, taken from the mockups, alongside the shared classes the phone's forms use (`card`, `field`, `button`). A member's color identifies them everywhere; tints are derived from it with `color-mix` rather than stored.

**Calendar change numbers.** `GET /api/calendar` includes `changeNumber`, a durable per-family `bigint` on `Family`. The endpoint uses a PostgreSQL repeatable-read transaction so the number, calendar sources, events and reconnect flag belong to one snapshot. `WheelhouseDbContext.SaveChanges` advances the number once per affected family in the same transaction as visible calendar changes, including demo seeds, series edits, Google sync and conflict refreshes. An etag-only change, sync token or sync timestamp does not advance it. Calendar sources must be removed through tracked deletes, not `ExecuteDelete`, so their removal and revision commit together. Deleting a member also advances the number because the database clears calendar ownership. A family's time-zone change advances it because it changes the day range's meaning. The counter is incremented directly in PostgreSQL; a tracked `Family` can hold an older value, so read the current number through an untracked query or projection. The hub publishes these numbers; the Angular store acknowledges them only when accepting a calendar snapshot.

**Calendar live notifications.** `/hubs/calendar` is a cookie-authenticated SignalR subscription for the `Family` policy. It has no client-callable methods. `CalendarConnections` assigns a family group from the authenticated claim and immediately sends `CalendarChanged({ changeNumber })`. Notifications contain no event data; clients must read their visible days through `GET /api/calendar`. `CalendarLiveService` checks committed revisions for subscribed families once a second, coalescing changes and retrying failed sends. This also recovers changes made in an outer transaction or by another process without publishing uncommitted state. With no subscribers it does no database work. The registry serializes joins, sends and revocations, checks the family and current account/device access before sending, and closes expired demo subscriptions even before cleanup. Sign-out, pairing into another family and removing a display close affected existing sockets; member removal/demotion revalidates subscriptions immediately. Cookie expiry also closes the connection. Browser Origin must match the request's public origin, after forwarded headers; nonbrowser clients may omit Origin but still need a valid cookie. Tests disable the publisher timer through `CalendarLive:Enabled` and publish explicitly, except the test of the worker. Existing `/hubs` proxy configuration already supports WebSockets. `CalendarLive` starts after session initialization and uses one cookie-authenticated `@microsoft/signalr` connection across all routes once `FamilyStore` has an authenticated family. It retries initial failures and reconnects every five seconds, refreshes after connection/reconnection and on visible-tab/online recovery, and owns the shared 30-second snapshot recovery timer for wall and phone. Socket callbacks are scoped to a generation; family switches, sign-out and revoked access stop the old socket and clear calendar data and counters. The service exposes connecting, connected, reconnecting, resyncing and stopped states plus `resync()` for the shared recovery controls. The server-health status line remains a fallback before the live subscription is available.

**Calendar client recovery.** `CalendarStore` tracks the revision of its accepted snapshot separately from the highest notification. Duplicate notifications do nothing; bursts coalesce into one read with a follow-up only if the response missed a newer revision. Forced recovery during a read queues one follow-up. Range changes and confirmed writes invalidate older reads, even if the user navigates away and back to the same range. Snapshot revisions cannot move backward. A failed background read keeps the last good state; unavailable first loads can be retried, and a 15-second HTTP timeout prevents a hung read from blocking recovery indefinitely. Reads never change the selected date, view, owner filters or open editor draft. Optimistic edits use the pending overlays described below; the shared connection controls expose snapshot progress and failure without resetting those overlays.

**Optimistic calendar edits.** `CalendarStore` retains each pending request, its original occurrence(s), source and family time zone. Temporary IDs show additions immediately; loaded series previews keep every occurrence's day, wall-clock time and length. `calendar-preview.ts` handles family-zone conversion, DST gaps/overlaps and monthly dates that skip short months. Event responses carry an opaque family-scoped `seriesId` rather than a Google identifier. Pending locks cover the same event and overlapping series operations; unrelated saves may proceed. Every layout shows save feedback, dims pending events and disables another edit. Editors freeze a submitted draft while saving or checking an uncertain result; validation/permission failures roll back only that overlay and keep the draft open. A 409 still presents Google's authoritative event through the existing conflict flow. Family reset discards operations and ignores late mutation responses.

**Uncertain saves and create retries.** A network error, server error or 20-second write timeout may follow a successful commit. Such operations stay marked uncertain, retain their exact request, and offer `Check save` from the editor or shared save feedback. Checking reads the affected day first; a matching authoritative result finishes without repeating the write. Otherwise a create retries with the same `creationId`. The API maps it to a deterministic, family-scoped Google-compatible event ID and serializes same-key creates with a PostgreSQL transaction advisory lock. Cached retries return the original occurrence without advancing the revision; if Google stored the event before a cache rollback, its 409 is reconciled by reading that same ID. The demo uses the same IDs and lock. `creationId` is returned on occurrences so a live snapshot can replace a temporary create before its POST response arrives. These identifiers use existing cache fields and need no migration. Only the insertion body sends Google's explicit ID; patches do not. A hard page reload does not persist in-memory pending drafts or operations.

**Calendar recovery controls.** `CalendarConnection` is shared by wall, phone Today and phone Calendar. Its pill reflects the actual live subscription: Connecting, Reconnecting or Live updates. `Resync now` refreshes the current server snapshot and explicitly replaces a disconnected socket; restarting the same family's subscription never resets calendar data, pending operations or filters. Background polling and reconnect completion only refresh snapshots and do not repeatedly replace the socket. `CalendarStore.refreshFailed` exposes quiet read failures while retaining the last accepted data; controls show progress, disable duplicate clicks during a read and offer a clear retry after failure. The old server-health line is only a fallback before a live subscription exists. Google's reauthorization notice is separate, with a Settings link for signed-in parents on the phone; resync never forces an upstream Google sync. Browser checks cover real SignalR handshake/drop/reconnect behavior over mocked WebSockets, failed resync, date/view/filter preservation, an open draft during recovery and touch sizes at wall and phone resolutions.

## Project rules

**Meals to groceries.** GET/POST `/api/meals/groceries` previews 1–7 local days and atomically adds 1–500 selected ingredients to the protected Grocery. Sources use the saved recipe JSON plus servings fingerprint, date/slot and ingredient ID; notes-only slot edits do not reset purchase counts. `GroceryContribution` retains original provenance after grocery edits/checks/tombstone clears and advances both meals and lists revisions. `GroceryBatch` stores an immutable request/result receipt and does not itself advance revisions. Batch writers acquire list lock 51 then meal lock 61; validate every source version, prior count, explicit repeat-purchase flag and optional unchecked target version. Combine only numeric quantities with whitespace/case-normalized exact names/units, without conversion. New items use Other; existing targets keep their category. Phone `MealGroceriesStore` keeps accepted previews separate from drafts and frozen pending batches, receives both domain hints/recovery/reset from `HouseholdLive`, and reconciles uncertain writes by retrying the receipt. Quantity text supports 100 characters to preserve saved recipes. Phone generation and shared grocery provenance use the existing tokens; wall generation controls are deliberately absent. See `docs/meal-groceries-design.md`.

**Saved recipes.** Recipes are family-owned with a composite family/ID key; parent PUT commands share meals' advisory lock and durable receipts. GET returns active and archived definitions plus the matching meals revision and parent management permission. Recipe changes advance the meals revision without rewriting slots. A slot stores a JSON recipe snapshot and independent whole-number servings. Numeric quantities scale from the snapshot's original quantities/default servings; text quantities and units are unchanged. Choose/refresh validates an active recipe ID and reviewed version in the current family. Copy preserves the saved snapshot, and explicit clear/free-text conversion removes it. `RecipesStore` activates on library/chooser use and receives meals-domain recovery/reset through `MealsStore`; pending recipe commands are frozen and receipted retries cannot reapply old saves. Phone parents manage the library; both layouts read and choose. See `docs/recipes-design.md`.

**Shared lists.** `/api/lists` is authorized for every family client, paired displays included. `HouseholdList` and `ListItem` use family query filters, create request fingerprints, immutable creation IDs and concurrency versions. Mutations serialize with a family advisory lock. Concurrent adds append independent rows; reorder checks the reviewed list version and swaps positions within checked/unchecked sections. Every item mutation also advances the list version. Explicit delete retains an internal tombstone for safe retries; archived lists and their contents remain readable. The snapshot (all lists, including archived, excluding deleted items) and `Family.ListsChangeNumber` are read in one repeatable-read transaction. The SaveChanges boundary advances only the lists counter for list/item/category changes; family deletion cascades all three tables. `DemoLists` seeds Grocery, Errands, Weekend packing and Household to-dos. `/hubs/household` sends independent `lists` and `chores` revisions after access validation. `ListsStore` activates on the list screen, retains confirmed data plus pending list overlays, rejects stale reads/replies and reconciles uncertain writes before retrying immutable commands. It clears data on family changes. `/lists` and `/wall/lists` share `ListsPage`, including quick-add drafts keyed by list, modal editing, checked items, move buttons, archive confirmation and read-only archived contents. See `docs/lists-design.md`.

**Grocery.** Every family has one protected `IsGrocery` list, enforced by a partial unique index; it cannot be renamed or archived. The migration backfills an empty Grocery and six categories without repurposing ordinary lists. `ParentSignIn` and demo seeding add Grocery before tracking the new family. Optional quantity text allows 100 characters and unit text 50 characters. `GroceryCategory` is family-owned; endpoints validate categories against the target list. Other stays last and cannot be removed/renamed; removing a category remaps items to Other and advances their versions. Category configuration uses the reviewed list version. Move operations remain within a category and checked state. `/clear-checked` receives only a frozen set of reviewed IDs/versions (1–500); any reopened/edited live target refuses the entire clear, deleted targets are satisfied and later checks are untouched. Unknown replies reconcile the frozen command, never a fresh all-checked predicate. The shared screen preserves quantity/category drafts and clear confirmations through live reads; Review latest explicitly reloads category/clear intent after a conflict. Automatic merging and meal-generated groceries remain deferred. See `docs/grocery-design.md`.

**Meal planning.** `/api/meals?from=&to=` reads 1–14 household-local days (exclusive end) in repeatable-read isolation, with all three slots and `Family.MealsChangeNumber`. `MealSlot` is family-owned and unique by family/date/slot; clearing keeps an empty versioned row to guard stale empty editors. A missing row has a null version and GET never materializes it. Family-authorized PUT `/api/meals/{date}/{slot}` and POST `/api/meals/copy` serialize with advisory lock seed 61. Successful immutable command IDs and normalized fingerprints are retained in family-owned `MealCommand` receipts; retries never reapply an older edit/copy/clear, including after later edits. Changed-body ID reuse conflicts. Copy validates every reviewed source and destination version before changing anything; unselected slots and source weeks remain unchanged. SaveChanges advances only the meals revision for slot mutations, not receipt-only/no-op commands. Family deletion cascades both tables. `DemoMeals` seeds relative current/previous weeks. Shared `MealsPage` provides `/meals` and `/wall/meals`; phone-only copying defaults occupied destinations to unselected. `TodayMeals` rolls over in the family zone. `MealsStore` separates confirmed ranges and pending commands, ignores stale replies and reconciles against original ranges before retrying the frozen receipted command. Editing pins the viewed week through midnight; recovery preserves drafts/choices, while family changes reset them. Meals stay separate from Google events. Saved recipe snapshots are introduced in 6.2; grocery generation is described below. See `docs/meals-design.md`.

**Repeating chores.** `ChorePlan` versions recurring definitions by family-local `EffectiveFrom`. Daily and selected-weekday every-N-weeks schedules have a start and optional inclusive end; weekly intervals anchor to the Monday of the start week. New definitions use the chosen start. Editing or archiving an existing schedule affects tomorrow onward, retaining today's and earlier plan snapshots. One-time definitions cannot be converted in place. `ChoreCompletion` is uniquely keyed by `(ChoreId, DueDate)`; only explicit completion commands write it. Each dated occurrence has an independent concurrency version and stable definition/date identity. Definition edits use a separate `definitionVersion`. Future repeats cannot be completed early; past missed occurrences can be completed/reopened using date navigation, including after the schedule is archived. Query filters scope both new tables, and family deletion cascades them through their definition.

**Repeat projection and recovery.** Chore reads project one requested day and load only that day's completion rows, without a midnight worker or writing on GET. Missed repeats stay in their dated history instead of becoming an accumulated overdue backlog; one-time overdue work behaves as before. Responses include the editable latest draft separately from the dated plan, visibility/missed flags and future change/stop dates. Chores endpoints accept a date query for reconciliation, required on repeating completion. Pending operations retain that original date after navigation; different dates may complete independently while schedule edits lock the definition. Shared chores revisions include plan/completion changes. The editor documents tomorrow's effective change and preserves its repeat controls through live recovery. DemoChores seeds daily, weekday and fortnightly examples; see docs/chores-design.md.

**One-time chores.** `Chores` stores family-owned, versioned one-time work with a family-local due date, optional member, completion instant and archive flag. `/api/chores` reads a repeatable-read snapshot and durable `Family.ChoresChangeNumber`. Parents create/edit/archive; family members and paired walls set completion to an explicit boolean. Commands serialize with a family transaction advisory lock; normalized create requests have immutable family-scoped creation IDs, so duplicate requests return the same row and changed-body key reuse conflicts. Stale conflicting versions return 409, while already-satisfied commands are no-ops. The shared SaveChanges boundary advances chores revisions atomically alongside writes, including member deletion; its SET NULL foreign key preserves a removed member's chore history. Family deletion cascades chores. `DemoChores` supplies fictional assigned, household, completed and overdue examples.

**Household live updates.** `/hubs/household` is a second shared authenticated subscription alongside the unchanged calendar hub. `HouseholdConnections` follows the calendar's family grouping, cookie expiry, Origin validation and access revalidation, publishing committed `HouseholdChanged({ domain: 'chores' | 'lists' | 'meals', changeNumber })` hints once a second only for subscribers. Sign-out, pairing and display removal close both sockets; member changes revalidate both registries. Tests disable `HouseholdLive:Enabled` except the worker test. Each domain has its own independent revision. `HouseholdLive` shares one browser subscription, retries initial and dropped connections, recovers snapshots on reconnect/resume and every 30 seconds, and clears state on a family/access change. `ChoresStore` separates confirmed rows from pending projections, ignores stale reads/late family responses, and checks uncertain saves before reusing their frozen creation ID/version.

**Chores screens.** Phone `/chores` and wall `/wall/chores` share `ChoresPage` with member/Household groups, overdue work, date selection and a collapsed completed section. Only phone parents see management controls; the API independently enforces permissions. Native modal editors preserve drafts through recovery, freeze submitted intent and keep uncertain operations available globally after closing. A stale conflict requires reviewing/reloading current values. Chore times are displayed in the family's zone; a completed overdue chore remains accessible on its due date. See `docs/chores-design.md` and `docs/household-roadmap.md` for scope and later increments.

- **This repository will be made public.** Never commit a real family's names, email addresses, the family instance's domain, or anything from a server's `.env`. Demo data is fictional and stays that way.
- **Every feature ships with its demo seed data** (built in `Demo/DemoFamily`) and a minimal phone screen alongside the wall view.
- **Touch targets** are at least 56 px on the wall and 44 px on the phone.
- **Confirmed state and pending intent stay separate.** `CalendarStore` renders optimistic overlays over its last confirmed snapshot. Live reads preserve them; definite failures remove only the refused operation, and successes retain their overlay until a snapshot started after acceptance replaces it. `FamilyStore` still changes only after server acceptance.
- **API tests run against real PostgreSQL** through `ApiFactory`. The `api` collection shares one container. `DemoVisitorAsync()` gives a client signed in as a parent of its own fresh copy of the demo family, which is how a test acts as a parent without touching another test's data. `DbContextFor(familyId)` reads and writes as a given family. Each test must pass when run alone.
- **Changes reach `main` through pull requests.** CI runs on pull requests and on `main`.


**Daily chore overview and history.** Phone Today selects the household's current date in `ChoresStore`, renders outstanding work and quick-complete controls, and rolls over with `Clock` in the family zone. Both chores layouts have member/status filters and wall member progress; filters do not change the underlying snapshot or pending commands. `ChoresStore.selectHistory(from, to)` uses `/api/chores/history` and the same durable revision, household subscription and recovery path as the daily view. The endpoint accepts an exclusive-end range of 1–31 due dates ending no later than tomorrow's start in the household zone. It reads one repeatable-read snapshot, projects repeating occurrences without writes, and includes archived one-time rows. History is current occurrence state with saved completion instants, not an audit log. A stopped series retains earlier actionable dates; archived one-time rows are read-only. Changing day/history invalidates older range reads, and recovery preserves the selected view, filters and drafts. New family identity clears view preferences; removed selected members fall back to Household. Demo history includes past completions and an archived example. See `docs/chores-design.md` for screen states and bounds.

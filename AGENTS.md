# AGENTS.md

Guidance for coding agents working in this repository. The README covers what Wheelhouse is and how to run it; this file covers what you need to change it safely. [docs/architecture.md](docs/architecture.md) draws the same architecture for people, and [docs/adr/](docs/adr/) records why the main choices were made: when a change alters one of those, update the diagram or add a decision record in the same pull request. Finished and deferred plans live in [docs/archive/](docs/archive/).

## Commands

Run these from the repository root unless a line says otherwise.

| Task | Command |
| --- | --- |
| Build the API and tests | `dotnet build` |
| API tests (Docker must be running) | `dotnet test` |
| One API test class | `dotnet test --filter "FullyQualifiedName~FamilyTests"` |
| One API test | `dotnet test --filter "DisplayName~A_family_sees_only_its_own_rows"` |
| Web tests, in `web/` | `npm test -- --watch=false` |
| One web spec file, in `web/` | `npm test -- --watch=false --include src/app/core/family.spec.ts` |
| Web tests by name, in `web/` | `npm test -- --watch=false --filter "is private"` |
| Web production build, in `web/` | `npm run build` |
| Wall/phone browser checks, in `web/` (build first) | `npm run test:e2e` |
| Whole app at http://localhost:8080 | `docker compose up --build -d` |
| Edit, drag and series checks against the running app, in `web/` | `npx playwright test -c playwright.stack.config.mjs` (`STACK_URL` for another address) |
| Database only, for running from source | `docker compose up db -d` |
| API from source, port 5080 | `dotnet run --project src/Wheelhouse.Api` |
| Web dev server, port 4200, in `web/` | `npm start` |
| Live Google check (needs a test account's secrets, see `docs/live-google-check.md`) | `dotnet test --filter "Category=LiveGoogle"` |
| New migration | `dotnet tool restore`, then `dotnet ef migrations add <Name> --project src/Wheelhouse.Api --output-dir Data/Migrations` |

The Playwright browser checks use stubbed API responses to hold and reject writes at wall and phone sizes; they verify immediate rendering, draft preservation and uncertain-response reconciliation. CI installs Chromium and retains screenshots/traces in `calendar-browser-checks`. Install the browser locally with `npx playwright install chromium` before running these checks.

The `stack` CI job builds the whole app with `docker compose`, runs `deploy/smoke.mjs` against the demo, runs `web/e2e-stack` (add, reload and delete; drag on the wall; renaming a whole series) against the real API and database, then restarts the API as a family instance and smoke checks that it shows nothing signed out. Each browser in those checks gets its own demo copy.

There is no linter. Prettier settings live in `web/.prettierrc` but are not enforced, and some files do not match them, so do not reformat files you are not otherwise changing.

The API tests start their own PostgreSQL with Testcontainers. They never use the Compose database. `LiveGoogleTests` are the exception that calls Google: they skip unless the `LIVE_GOOGLE_*` variables are set, and `live-google.yml` runs them on demand (no schedule until its secrets are set) against a test account's calendar. When the Google client learns something new, add it there as well as to `FakeGoogle`. Before a calendar release, run the manual [parity checklist](docs/calendar-parity-checklist.md).

## Architecture

**One web app, two layouts.** `web/` is a single Angular app. `/wall` is the wall display (a 1920 × 1080 touch screen in kiosk mode) and `/` is the calendar for phones and desktop browsers (`home/calendar-home.ts`): bottom tabs below 768 px, a rail from 768 px, switching with the window width without a route change; `/calendar` redirects to it. Each context (phone, desktop, wall) remembers only its last view in `localStorage` (`ViewPreferences`). Week is drawn on a shared, unit-tested grid engine (`core/calendar-grid.ts`): per-day segments of timed events in the family's zone, overlaps side by side (on Week more than two, on Day more than three, collapse into "+N"), and all-day or 24-hour-plus events as bars in an all-day lane. The wall fits its hours (7 AM to 9 PM, grown to fit) without scrolling; a desktop window scrolls the whole day. Day uses the same hour grid (`wall/hour-grid.ts`) with a column per person; Month (`wall/month-view.ts`) draws bars and a line per timed event under one button per day, as many lines as the card's height fits. The phone's Week and Month list events as compact rows (`home/compact-agenda.ts`). Tapping an event opens its details first (`shared/event-details.ts`: a drawer on the wall and desktop, a sheet on the phone, read-only events included); Edit and Delete there open the existing editors, and Duplicate opens a new event like it (`copyOf`: same title, place, times, notes, people and privacy, not repeating or counted down, in its calendar or the first that takes new events, so a read-only event can be copied too); details and editors hold keyboard focus and return it to the event (`shared/modal-focus.ts`), and tapping an empty half hour on the grid starts a new event at it. The wall's editor, which a desktop window shares, steps times by 15 minutes and also takes a typed time (`parseClock` in `core/event-draft.ts`: "3pm", "3:30 PM", "15:30"; an hour alone leans to the family's day for a start and to after the start for an end, and a typed end before the start ends it the next day); the phone's sheet uses the browser's time fields. On the Week and Day grids (wall and desktop) a writable event can be dragged to another time, or on Week another day, keeping its length (`wall/hour-grid.ts`): a mouse or pen drags once it moves, a finger holds the event for a moment first so taps and scrolling still work, the start snaps to the editor's 15-minute steps, Escape lets go, and the drop saves through `CalendarStore.update` as an optimistic edit. Day keeps an event in its person's column. Pulling a writable event's bottom edge changes when it ends the same way (15-minute steps, at least 15 minutes long, no later than midnight), on the day it both starts and ends. A repeating event asks This event or All events, offering All events only when the day is unchanged, since a whole series keeps each event's own day. A timed event starting within 10 minutes (`SOON_MINUTES`) gets a ring and reads "In N min" on the grids. Week headings show each day's forecast (`shared/day-forecast.ts`) on the wall, desktop and phone. Both talk only to the API. A desktop window answers to keys (`shared/shortcut-help.ts`): T today, J/N and K/P to step, D/W/M for the views, C for a new event, E and Delete for the open event's editor, and ? to list them; never while typing, with a modifier, or with an editor open. Settings live only on the phone, under `/settings`; the wall has none. State lives in root-provided stores under `web/src/app/core/` that expose read-only signals; components are standalone, the app is zoneless, and small components keep their template and styles inline.

**API by feature.** `src/Wheelhouse.Api/` is ASP.NET Core minimal APIs in feature folders (`Families`, `Demo`, `Auth`, `Devices`, `Calendar`, `Weather`, `Sessions`, `Health`, `Diagnostics`). Each feature exposes a `MapX()` extension that `Program.cs` calls.

**Instance mode.** The same image runs as two kinds of instance, chosen by `Wheelhouse:Mode` (`WHEELHOUSE_MODE` in a deployed instance's `.env`):

- `Family` is a real family's private instance. Nothing is readable without signing in. It is the default when the setting is missing, and it must stay the default.
- `Demo` is the public demo. Each visitor gets a private copy of a fictional family (`Demo/DemoCopies`) and is signed in to it as a parent. A copy is a family row with `ExpiresAt` set, deleted an hour or less after it expires, or sooner when the demo holds `MaxDemoCopies` and a newcomer's copy replaces the oldest, so the demo never turns a visitor away for being full; copies are admitted one at a time under an advisory lock. A copy holds at most `MaxDemoEvents` events, and a demo repeating event starts no more than 90 days back, so one write expands a bounded number of occurrences. A real family has no `ExpiresAt`, so cleanup can never delete one.

Local development and `docker compose up` run as `Demo`.

**Family scoping.** Every table that holds a family's data implements `IFamilyOwned`. `WheelhouseDbContext` gives each of those a query filter on `CurrentFamilyId`, which comes from the signed-in principal's `wheelhouse:family` claim through `ICurrentFamily`. Outside a request there is no current family and filtered queries return nothing. Code that runs without a request, such as the demo seeder, must opt out with `IgnoreQueryFilters()` on purpose.

**Authorization.** Everyone is authenticated by one encrypted cookie that carries their family's id. On a demo instance `POST /api/demo/visit` issues it; that endpoint is the only sign-in without an account and answers 404 on a family instance. The web app calls it in an app initializer, so the cookie exists before any screen loads data; `index.html` shows "Starting Wheelhouse…" until then, and each startup request gives up after `START_TIMEOUT_MS` (`core/session.ts`), so a hung request still lets the app start and say what went wrong. On a family instance a parent signs in with Google: `GET /api/auth/google` sends the browser to Google, which returns it to `/api/auth/google/callback`, where `ParentSignIn` admits only verified addresses listed in `Wheelhouse:ParentEmails` and links each Google account (`UserAccount`, by Google's subject id) to a parent member. The first parent to sign in creates the family. A parent's cookie also carries their account id and is re-checked on every request, so removing them from the family or from the list signs them out. Google is used for identity only here; Calendar access is a separate connection (see Calendar). A wall display signs in by pairing (`Devices/Pairing`): it asks `POST /api/pairing` for a 6-digit code, a parent enters the code on their phone (`POST /api/devices`), and the display's next `POST /api/pairing/{id}/finish` gives it the same cookie, carrying its device id instead of an account. The cookie lasts a year and slides; each request re-checks the device row and updates its `LastSeenAt`, so a parent removing the display from Settings signs it out at once. A display reads the family but is not a parent; `/api/session` says `isDisplay`, so Settings tells a display what it is and offers only Sign out. On the demo, a wall starts with its own copy and its "Pair with a phone" button joins the phone's copy. The demo never calls Google. Endpoints require the `Family` policy (anyone signed in to a family) or the `Parent` policy. `Family` is also the fallback, so an endpoint that names no policy still needs a sign-in; anything only a parent may do needs `RequireAuthorization(Policies.Parent)`. Only `/health`, `/api/session`, `/api/demo/visit`, `/api/auth/google` and the display's two pairing endpoints are open, through `AllowAnonymous()`, and `AccessTests` fails if that list changes. A browser request that changes anything (any method but GET, HEAD and OPTIONS) and every `/hubs` request must carry this site's own Origin when it carries one (`Auth/SameOrigin`), because the instances share a registrable domain and `SameSite=Lax` treats sibling subdomains as one site. On a family instance the last parent who can sign in (a linked Google account still on the parent list) cannot be demoted or removed. Every request is rate limited (`Auth/RateLimits`): 600 a minute and 120 changes a minute per signed-in family, or per address for anyone else; asking for pairing codes, guessing them and making demo copies have their own tighter limits.

**Calendar.** Google Calendar is the source of truth for events; the API keeps a cache of it. `CalendarSource` is one Google calendar the family shows, owned by a member or, with no member, by the whole family, and `EventInstance` is one occurrence of an event, as Google expands recurring ones. A timed event is stored as UTC instants, an all-day one as dates with an exclusive end, as Google does. `GET /api/calendar?from=&to=` takes the family's own days, in its time zone, and the web app turns instants into days with `core/days.ts` rather than the browser's zone. The demo seeds a copy's calendars in `Demo/DemoSeedData`, relative to the day the copy is made, and never calls Google. Anyone signed in to the family, a paired wall included, adds, changes and deletes events through `/api/calendar/events` (`EventEndpoints`): each change goes to Google first with the cached occurrence's etag in `If-Match`, then the cache takes what Google stored. Google's 412 answers 409 with Google's current version, which the screens show instead; each occurrence also carries an opaque `version` (`EventVersion`, a hash of what the screens show of it, not Google's etag), which a change sends in its body and a delete as `?version=`, and a version that is no longer the cached one answers 409 with the event as it is now, so a draft opened before another screen's save cannot overwrite it (a request without one is still accepted); a change to one occurrence of a repeating event changes only that occurrence. A new event, or an existing one that does not repeat yet, can repeat by an RRULE in `recurrence` (`RepeatRules`: every N days, weeks on chosen weekdays, months on a date or a weekday's place in the month, or years, ending never, on a day or after a number of events; the API validates and rewrites it, ending a timed series at the end of the family's last day as Google wants; the older `repeat` field still works). An existing event becomes the series' first event and the calendar is read again for its occurrences. `?series=true` on a change or delete applies to the whole series (`EventSeries`): Google's series is patched through its first event, every occurrence keeps its own day, a new `recurrence` replaces the series' rule and Google expands it again from its first event, and the calendar is read again at once because Google gives the occurrences new versions and often new ids. `?following=true` (This and following) splits a series: Google's series is ended the day before with `UNTIL` (a `COUNT` becomes the count left, carried to the new series) and the event and later ones are inserted as a new series, new one first so a failure shows events twice rather than losing them; on its first event it means the whole series, and a delete with it only ends the series. The editors' Repeat row (`shared/repeat-picker.ts`) offers the usual repeats named from the first day and a Custom part; a ready-made repeat follows a new event's first day, rules are compared and sent in one canonical form (`canonicalRule`), only when changed, and previews expand them with `ruleDays`, which matches the API's expansion. On the demo the change goes straight to the copy's cache, which expands a new series itself. A calendar the shared account cannot write to (`CanWrite`) is shown but takes no changes. The cache also keeps each event's notes (`Description`, Google's text, which may be simple HTML) and its series' rule (`Recurrence`, read from each series' first event while listing, since Google's expanded occurrences carry none). Details show the rule in words (`core/repeat-rule.ts`) and the notes as text (`core/notes.ts`); the editors send `description` only when the notes changed, so an edit or a drag never rewrites HTML notes as plain text. An event is for its calendar's owner and any other members a hidden tag names (`EventInstance.MemberIds`, kept in Google as the private extended property `wheelhouseMembers`, which other Google Calendar apps never show); the editors' Who chips set it and send `memberIds` only when they changed, and left out a change keeps them. `ownersOf`/`peopleOf` in `core/calendar.ts` say whose an event is: the chips' filter shows it while any of its people is shown, Day puts it in each one's column in that person's color, and Week, details and labels name them all. An event private in Google (`visibility` private or confidential, `EventInstance.IsPrivate`) reaches a paired display only as busy: `GET /api/calendar` and an endpoint filter on `/api/calendar/events` send it through `EventResponse.AsBusy` (title "Busy", no place or notes, `hidden`), a display gets 403 changing or deleting one, or a whole series or later events that hold one, and cannot make one private, and the screens treat a hidden event as read-only. Parents set Private in either editor; `private` is sent only when it changed, so a change never touches Google's visibility otherwise. Count down (`EventInstance.Countdown`, the private extended property `wheelhouseCountdown`, "1" when set) marks an event for the countdown chips on the wall's toolbar and the phone's Day (`core/countdowns.ts`, `shared/countdown-strip.ts`); anyone in the family sets it in either editor and `countdown` is sent only when it changed. `GET /api/calendar/countdowns?from=` gives the next three marked events from a family day, one per series, never a private one to a display; `CountdownStore` reads it again when the family's day turns and with each newer calendar change number, retries a failed read after 30 seconds, and drops another family's countdowns at once on a switch. On the wall the end grip reaches up to 40 px into free time below an event, never over the next one.

**Google connection.** A family's calendars come from one shared Google account, not from the parents' own. A parent connects it from Settings: `GET /api/calendar/google/connect` sends the browser to Google's consent screen for Calendar with offline access, and `/api/calendar/google/callback` stores the refresh token in `GoogleConnection`, encrypted with Data Protection (`GoogleTokens`), whose keys live on their own volume. The consent's `state` is signed and names the family, so a code cannot be attached to another family. `GET`/`PUT /api/calendar/sources` list the account's calendars and choose which show and whose each is; without a connection (the demo) they list the calendars the family already has. Google's `invalid_grant` marks the connection `NeedsReauth`; Settings asks a parent to connect again, and `GET /api/calendar` says `needsReconnect` so the wall shows a notice. On a family instance `CalendarSyncService` syncs every connected family every two minutes (`CalendarSync:Interval`), and at once after a parent connects or chooses calendars (`CalendarSyncTrigger`). `CalendarSync` asks each calendar what changed since its sync token and only then, or once a day as the window moves, reads its events from 90 days back to 400 ahead and replaces the cache. `GET /api/calendar` says which family days that window holds (`syncedFrom`, `syncedTo`; absent on the demo), and the screens say "Synced through …" and "Not synced this far" rather than calling days past it empty; Google's 410 for an old token means a full read. Google is read outside any transaction, so a pass reads the family's change number first and replaces the cache in a repeatable-read transaction only if it has not moved; a screen's save that commits meanwhile makes the pass give up on that calendar, keeping its sync token, so the next pass reads it again instead of overwriting the save with Google's older answer. The `calendar` health check turns `Degraded` when a pass fails or a connection needs reconnecting. Wall and phone subscribe to committed calendar changes through SignalR and fetch their visible days when notified. A shared 30-second recovery check catches missed notifications; Google’s two-minute worker still discovers upstream edits. The tests turn the worker off and run `CalendarSync` themselves. All Google calls go through `IGoogleCalendar`; `GoogleCalendarApi` is plain HTTP to Google's REST endpoints, and the tests replace it with a fake. `/privacy` is the page Google asks for before the OAuth app can be published.

**Weather.** `GET /api/weather` is today's weather where the family lives, with the next seven days' forecast (`days`, by the family's dates), from Open-Meteo (no key), cached for 30 minutes per place, so demo visitors share one forecast. A parent sets the place from their phone in Settings (`PUT /api/family/location`), kept to two decimal places. With no place it answers 204, and 503 when Open-Meteo cannot be reached; the screens then leave the weather out. Tests replace Open-Meteo's handler and never call it.

**Client errors.** The web app's `ErrorHandler` (`core/error-reporting.ts`) logs to the console and also posts each error to `POST /api/client-errors` (`Diagnostics`), once per message and at most five in ten minutes, so a wall nobody watches still leaves its errors in the API's log with its family and device.

**Startup.** `PrepareDatabaseAsync` applies migrations before the API takes requests. If the database cannot be reached the process exits and the container's restart policy retries.

**Configuration is read late.** Read settings inside a DI factory or through `IOptions`, not from `builder.Configuration` while registering services. The integration tests add their overrides in a way that only takes effect once the host is built, so an early read sees the wrong database or mode.

**Deploy.** Every push to `main` runs `release.yml` (as does a `v*` tag or a manual run with a version): tests (`ci.yml`, which otherwise runs only on pull requests), then, unless held (`release:hold` label, `[no release]` in the merge commit, or the `AUTO_RELEASE` variable set to `off`), the next version's tag (patch bump, or minor/major by the `release:minor`/`release:major` labels of the pull requests since the last tag), images to GitHub Container Registry, then `deploy/release-phase.sh`, which runs `deploy/deploy.sh` on the server for the `Demo` instances under `~/wheelhouse/*/` and browser-checks them, and only then does the same for the `Family` instances, and finally the GitHub release with generated notes. Each instance is its own Compose project from `deploy/compose.yaml` with its own database, network and secrets. `deploy/new-instance.sh` creates an instance's folder, `.env` and nginx site on the server; `deploy.sh` warns about a family instance whose Google sign-in is not filled in. `deploy.sh` also snapshots every instance on the server before migrating; separately, `nightly-backup.sh` (a systemd timer that `install-maintenance.sh` installs) uploads each instance's dump, Data Protection keys and `.env` to a Cloud Storage bucket the VM can only add to, in the layout `restore.sh` reads. The server's nginx terminates HTTPS and forwards to the instance's web container on a loopback port; that container serves the Angular build and forwards `/api`, `/hubs` and `/health` to the API. Its `nginx.conf` sets the security headers, including a Content-Security-Policy that allows scripts only from the site, so `angular.json` turns off critical-CSS inlining (its loader is an inline script); keep new code free of inline scripts and of other origins beyond Google Fonts. It also gzips the app's own files (not API responses) and lets browsers keep the build's hashed files for a year, while the app shell is checked again on each load. The API reads `X-Forwarded-Proto` and `X-Forwarded-For` from the server's nginx, so it knows a visitor came over HTTPS and marks the sign-in cookie `Secure`.

**Look and feel.** Colors, fonts, radii, borders and shadows are design tokens in `web/src/styles.css`, taken from the mockups, alongside the shared classes the phone's forms use (`card`, `field`, `button`). Components never use raw values. A member's color identifies them everywhere; fills, rings, avatars and time labels are mixed from it under `[style*='--member']` (`--member-bg`, `--member-strong`, `--member-time` and so on) with percentages and bases each theme sets, so a theme changes how a color is drawn but never its hue. Whole-family events use `FAMILY_COLOR`, which is the `--family` token. A member can also choose one of the built-in pictures (`core/avatars.ts`, drawn in `web/public/avatars/` on a transparent background; the API accepts the same ids in `Families/MemberAvatars`). `shared/avatar-face.ts` draws the picture, or the initial without one, inside every avatar circle, so the circle keeps the member's color in every theme.

**Themes.** A family chooses Daylight (the default), Groovy, Classic or Bold (`Family.Theme`), and Night mode: Off, AtNight (the default) or Always (`Family.NightMode`), both through `PUT /api/family/theme` for parents. `core/theme.ts` sets `<html data-theme>` from the family store and `data-night` always, or while the family's clock is between `nightModeFrom` and `nightModeTo`, and loads only the active theme's web fonts; Outfit and Figtree, used by Daylight, come from `index.html`. Each theme is one token block in `styles.css` that starts from Daylight's. Each also has a dark look: `[data-night]` sets every color to Daylight's dark one, and `[data-theme='…'][data-night]` sets that theme's dark colors on top, keeping its shapes, outlines and fonts. An element with its own `data-theme` and `data-night` (the Settings previews) takes that look's tokens. Devices pick up a new theme through the shared 30-second check, which also refreshes the family. `core/contrast.spec.ts` checks every look's tokens, light and dark, for every member color, so add a token's text/background pair there when you add one.

**Calendar change numbers.** `GET /api/calendar` includes `changeNumber`, a durable per-family `bigint` on `Family`. The endpoint uses a PostgreSQL repeatable-read transaction so the number, calendar sources, events and reconnect flag belong to one snapshot. `WheelhouseDbContext.SaveChanges` advances the number once per affected family in the same transaction as visible calendar changes, including demo seeds, series edits, Google sync and conflict refreshes. An etag-only change, sync token or sync timestamp does not advance it. Calendar sources must be removed through tracked deletes, not `ExecuteDelete`, so their removal and revision commit together. Deleting a member also advances the number because the database clears calendar ownership. A family's time-zone change advances it because it changes the day range's meaning. The counter is incremented directly in PostgreSQL; a tracked `Family` can hold an older value, so read the current number through an untracked query or projection. The hub publishes these numbers; the Angular store acknowledges them only when accepting a calendar snapshot.

**Calendar live notifications.** `/hubs/calendar` is a cookie-authenticated SignalR subscription for the `Family` policy. It has no client-callable methods. `CalendarConnections` assigns a family group from the authenticated claim and immediately sends `CalendarChanged({ changeNumber })`. Notifications contain no event data; clients must read their visible days through `GET /api/calendar`. `CalendarLiveService` checks committed revisions for subscribed families once a second, coalescing changes and retrying failed sends. This also recovers changes made in an outer transaction or by another process without publishing uncommitted state. With no subscribers it does no database work. The registry serializes joins, sends and revocations, checks the family and current account/device access before sending, and closes expired demo subscriptions even before cleanup. Sign-out, pairing into another family and removing a display close affected existing sockets; member removal/demotion revalidates subscriptions immediately. Cookie expiry also closes the connection. Browser Origin must match the request's public origin, after forwarded headers; nonbrowser clients may omit Origin but still need a valid cookie. Tests disable the publisher timer through `CalendarLive:Enabled` and publish explicitly, except the test of the worker. Existing `/hubs` proxy configuration already supports WebSockets. `CalendarLive` starts after session initialization and uses one cookie-authenticated `@microsoft/signalr` connection across all routes once `FamilyStore` has an authenticated family. It retries initial failures and reconnects every five seconds, refreshes after connection/reconnection and on visible-tab/online recovery, and owns the shared 30-second snapshot recovery timer for wall and phone. Socket callbacks are scoped to a generation; family switches, sign-out and revoked access stop the old socket and clear calendar data and counters. The service exposes connecting, connected, reconnecting, resyncing and stopped states plus `resync()` for the shared recovery controls. The server-health status line remains a fallback before the live subscription is available.

**Calendar client recovery.** `CalendarStore` tracks the revision of its accepted snapshot separately from the highest notification. Duplicate notifications do nothing; bursts coalesce into one read with a follow-up only if the response missed a newer revision. Forced recovery during a read queues one follow-up. Range changes and confirmed writes invalidate older reads, even if the user navigates away and back to the same range. Snapshot revisions cannot move backward. A failed background read keeps the last good state; unavailable first loads can be retried, and a 15-second HTTP timeout prevents a hung read from blocking recovery indefinitely. Reads never change the selected date, view, owner filters or open editor draft. While another range loads, `calendars` keeps the last snapshot's calendars so columns, chips and Add event stay put, and the views say they are loading or could not load rather than showing an empty grid. `show()` reads its state untracked, so a view's effect does not re-request after a failed read. Optimistic edits use the pending overlays described below; the shared connection controls expose snapshot progress and failure without resetting those overlays.

**Optimistic calendar edits.** `CalendarStore` retains each pending request, its original occurrence(s), source and family time zone. Temporary IDs show additions immediately; loaded series previews keep every occurrence's day, wall-clock time and length. `calendar-preview.ts` handles family-zone conversion, DST gaps/overlaps and monthly dates that skip short months. Event responses carry an opaque family-scoped `seriesId` rather than a Google identifier. Pending locks cover the same event and overlapping series operations; unrelated saves may proceed. Every layout shows save feedback, dims pending events and disables another edit. Editors freeze a submitted draft while saving or checking an uncertain result; validation/permission failures roll back only that overlay and keep the draft open. A 409 still presents Google's authoritative event through the existing conflict flow. Family reset discards operations and ignores late mutation responses. For ten seconds after a delete or change of one event that does not repeat, or of one occurrence, saves, `CalendarStore.undoable` offers Undo in the shared save toast: `undo()` adds a deleted event back or puts a changed one back as it was, through the same optimistic operations (notes, people and privacy only when the change touched them). Series, later-events and new-series changes offer none.

**Uncertain saves and create retries.** A network error, server error or 20-second write timeout may follow a successful commit. Such operations stay marked uncertain, retain their exact request, and offer `Check save` from the editor or shared save feedback. Checking reads the affected day first; a matching authoritative result finishes without repeating the write. Otherwise a create retries with the same `creationId`. The API maps it to a deterministic, family-scoped Google-compatible event ID and serializes same-key creates with a PostgreSQL transaction advisory lock. Cached retries return the original occurrence without advancing the revision; if Google stored the event before a cache rollback, its 409 is reconciled by reading that same ID. The demo uses the same IDs and lock. `creationId` is returned on occurrences so a live snapshot can replace a temporary create before its POST response arrives. These identifiers use existing cache fields and need no migration. Only the insertion body sends Google's explicit ID; patches do not. A hard page reload does not persist in-memory pending drafts or operations.

**Calendar recovery controls.** `CalendarConnection` is shared by the wall and `/`. It shows a small Live dot while the subscription is up and a quiet Connecting… before the first connection; Reconnecting (with the time the screen shows) and a failed refresh are pills with one action. On the phone the dot sits in the header and problems are banners. `Resync now` refreshes the current server snapshot and explicitly replaces a disconnected socket; restarting the same family's subscription never resets calendar data, pending operations or filters. Background polling and reconnect completion only refresh snapshots and do not repeatedly replace the socket. `CalendarStore.refreshFailed` exposes quiet read failures while retaining the last accepted data; controls show progress, disable duplicate clicks during a read and offer a clear retry after failure. The old server-health line is only a fallback before a live subscription exists. Google's reauthorization notice is separate, with a Settings link for signed-in parents on the phone; resync never forces an upstream Google sync. Browser checks cover real SignalR handshake/drop/reconnect behavior over mocked WebSockets, failed resync, date/view/filter preservation, an open draft during recovery and touch sizes at wall and phone resolutions.

## Project rules

**Calendar-first release scope.** Chores, shared to-do lists, groceries, meals and recipes are deferred. Do not reintroduce their routes, endpoints, services, SignalR transport, demo fixtures, or tests without an explicit new feature decision. Their old design docs and [household roadmap](docs/archive/household-roadmap.md) are historical/future planning references, **not active implementation specifications**. See [calendar-only scope](docs/calendar-only-scope.md).

**Legacy data only.** `Chore`, `ChorePlan`, `ChoreCompletion`, `HouseholdList`, `ListItem`, `GroceryCategory`, `MealSlot`, `MealCommand`, `Recipe`, `GroceryBatch`, and `GroceryContribution` remain as EF persistence shapes only. Existing migrations, the model snapshot, relationships, revision columns and DB records must not be dropped or altered as collateral during calendar work. They are not live features; avoid adding behavior to those types. A dedicated future archival/data-deletion decision is required before removal of their mapping.

- **This repository will be made public.** Never commit a real family's names, email addresses, the family instance's domain, or anything from a server's `.env`. Demo data is fictional and stays that way.
- **Every feature ships with its demo seed data** (built in `Demo/DemoFamily`) and a minimal phone screen alongside the wall view.
- **Touch targets** are at least 56 px on the wall and 44 px on the phone.
- **Confirmed state and pending intent stay separate.** `CalendarStore` renders optimistic overlays over its last confirmed snapshot. Live reads preserve them; definite failures remove only the refused operation, and successes retain their overlay until a snapshot started after acceptance replaces it. `FamilyStore` still changes only after server acceptance.
- **API tests run against real PostgreSQL** through `ApiFactory`. The `api` collection shares one container. `DemoVisitorAsync()` gives a client signed in as a parent of its own fresh copy of the demo family, which is how a test acts as a parent without touching another test's data. `DbContextFor(familyId)` reads and writes as a given family. Each test must pass when run alone.
- **Changes reach `main` through pull requests.** CI runs on pull requests and on `main`, and must pass before a pull request merges; a release tests its tag before publishing.
